# Castro’s Platform — Canonical Persona & Screen Architecture

Status: **AUTHORITATIVE PRODUCT ARCHITECTURE**

This document defines who uses the platform, which experience each person receives, and how screens map to responsibilities and permissions. Screen architecture must follow personas; RBAC exists to enforce the resulting responsibilities, not to invent the information architecture after the fact.

## 1. Canonical personas

The platform has exactly four product personas for the current scope.

### 1. Client / Customer
- External person or organization.
- No internal RBAC role is required for the V1 public journey.
- Uses the public website, discovery flows, contact and booking.
- Never enters organization operations or platform administration.

### 2. Secretary / Operations
- Primary day-to-day internal operator.
- Handles the operational workload generated by customers.
- Creates and manages bookings, requests, customer records, follow-ups and schedule changes.
- May maintain operational catalog/availability/content where the organization delegates this responsibility.
- Must not receive organization access administration or platform administration by default.

### 3. CEO / Owner
- Organization owner / executive persona.
- Not a daily operator.
- Needs a polished executive dashboard and complete visibility over the organization without being forced through operational administration workflows.
- Primary interaction mode: **see → understand → decide**.
- Can receive exceptional administrative authority, but authority must not force every technical/operational screen into the primary executive navigation.

### 4. RIGHTWARE Super Admin
- Platform-level operator controlled by RIGHTWARE.
- Does not belong to the Castro’s organization role hierarchy.
- Manages the platform/tenants, technical health, platform security, global audit and support capabilities.
- Must live in a separate platform administration experience.

There is **no separate Manager persona**. Management responsibilities are distributed between Secretary (operational management) and CEO/Owner (executive/company management).

## 2. Experience boundaries

```text
CASTRO'S SERVICES PLATFORM

A. CUSTOMER EXPERIENCE
   Persona: Client
   Namespace: public routes (`/`, `/servicos`, `/formacao`, `/espacos`, `/contacto`, `/reservar/...`)

B. OPERATIONS EXPERIENCE
   Persona: Secretary
   Namespace: `/app/...`

C. EXECUTIVE EXPERIENCE
   Persona: CEO / Owner
   Namespace: `/owner/...`

D. PLATFORM ADMINISTRATION
   Persona: RIGHTWARE Super Admin
   Namespace: `/platform/...`
```

The four experiences may reuse domain components and APIs, but they must not share one undifferentiated navigation model.

## 3. Screen architecture

### 3.1 Client screens

| Screen | Route family | Purpose |
|---|---|---|
| Homepage | `/` | Discover Castro’s |
| Services catalog | `/servicos` | Browse services |
| Service detail | `/servicos/:slug` | Understand and start booking |
| Formation catalog | `/formacao` | Browse formation |
| Course detail | `/formacao/:slug` | Understand sessions and booking |
| Spaces catalog | `/espacos` | Browse spaces |
| Space detail | `/espacos/:slug` | Understand space |
| Space explorer | `/espacos/:slug/explorar` | Explore real media/360 state |
| Space configurator | `/espacos/:slug/configurar` | Configure purpose/participants/layout context |
| Contact | `/contacto` | Submit a request |
| Booking — Date | `/reservar/:type/:id/data` | Select date |
| Booking — Time | `/reservar/:type/:id/horario` | Select an available slot |
| Booking — Customer data | `/reservar/:type/:id/dados` | Capture booking identity/contact |
| Booking — Review | `/reservar/:type/:id/rever` | Confirm intent |
| Booking — Confirmation | `/reservar/confirmacao/:reference` | Confirm successful booking |

### 3.2 Secretary / Operations screens

Primary navigation must optimize repeated daily work.

| Screen | Default responsibility | Permission family |
|---|---|---|
| Operations dashboard | Today, pending work, alerts, shortcuts | `dashboard.read` |
| Calendar / Agenda | Daily/weekly operational schedule | `booking.read` |
| Bookings | Search and manage bookings | `booking.read/create/update/cancel` |
| New manual booking | Phone/in-person booking | `booking.create` |
| Requests | Intake and follow-up | `request.read/create/update/assign/close` |
| Customers | Customer identity/history | `customer.read/create/update` |
| Tasks | Follow-up work | `task.read/manage` |
| Notifications | Operational alerts | `notification.read` |
| Availability | Working hours, exceptions and blocks when delegated | `availability.read/manage` |
| Services | Maintain operational service catalog when delegated | `service.read/manage` |
| Formation / sessions | Maintain operational formation schedule when delegated | `course.read/manage` |
| Spaces | Maintain operational space catalog when delegated | `space.read/manage` |
| Content | Maintain approved operational/public content when delegated | `content.read/manage` |

Secretary does **not** receive these by default:
- users administration;
- roles administration;
- permission administration;
- organization security/audit administration;
- RIGHTWARE platform administration.

### 3.3 CEO / Owner screens

The executive experience is intentionally different from Operations. It is not a duplicate admin sidebar.

| Screen | Purpose | Expected interaction |
|---|---|---|
| Executive Dashboard | Immediate company status | Primary screen |
| Agenda Overview | Understand upcoming activity and capacity | Read-oriented |
| Requests Overview | Understand demand and unresolved opportunities | Read-oriented |
| Reservations Overview | Understand bookings and status mix | Read-oriented |
| Customers Overview | Understand customer activity | Read-oriented |
| Executive Reports | Trends and operational performance | Analytical |
| Services Overview | Portfolio/status visibility | Read-oriented |
| Formation Overview | Sessions/activity visibility | Read-oriented |
| Spaces Overview | Utilization/availability visibility | Read-oriented |
| Team Overview | Internal accounts/roles at a business level | Read-oriented |
| Audit / Important Activity | Accountability and significant administrative changes | Read-oriented |
| Organization Settings | Critical organization configuration | Exceptional administration |
| Advanced Administration | Optional escape hatch for exceptional owner actions | Secondary, not primary navigation |

#### Executive Dashboard design requirement

The CEO dashboard must be visually polished and substantially different from the Secretary dashboard. It should prioritize:
- current operational state;
- upcoming bookings/activity;
- unresolved requests;
- customer activity;
- booking/status distribution;
- service/formation/space activity;
- recent important changes;
- concise trends using real data only;
- clear links to deeper executive views.

It must **not** become a generic SaaS card wall and must not fabricate revenue, conversion or performance metrics that the backend does not support.

### 3.4 RIGHTWARE Super Admin screens

Platform administration is a different security boundary and route namespace.

| Screen | Purpose |
|---|---|
| Platform Dashboard | Overall platform state |
| Organizations | Tenant/organization inventory |
| Organization Detail | Tenant status/configuration/support context |
| Platform Administrators | RIGHTWARE privileged accounts |
| Platform Health | Application/database/runtime health |
| Platform Security | Security posture/configuration state |
| Global Audit | Cross-tenant platform audit where legally/technically appropriate |
| Support Access | Explicit controlled support workflows |
| Platform Configuration | Platform-level settings/features |

Super Admin must not automatically behave as a Castro’s Secretary or CEO. Any support access into tenant data must be explicit, auditable and least-privileged.

## 4. RBAC rules

The implementation order is:

```text
Persona
  → Responsibility
  → Screen
  → Allowed action
  → Permission
  → Role assignment
```

Not:

```text
Permission list
  → hide random links
  → call the result a persona
```

### Shared screens are allowed

A shared domain screen/component may be reused by Secretary and CEO, but presentation and available actions must match the current experience.

Example:
- Secretary booking detail: operational actions visible.
- CEO booking detail/overview: read-oriented by default.

### Authorization and navigation are separate

A CEO may technically hold broad authority while still receiving a concise executive navigation. Permission possession must never force irrelevant operational/technical menu items into the CEO primary experience.

## 5. Booking/availability business model

The booking engine remains slot-based and resource-aware.

Supported public bookable targets:
- `SERVICE`
- `SPACE`
- `COURSE_SESSION`

Availability is calculated from:
- weekly rules;
- opening/closing times;
- slot interval;
- service/session duration;
- buffer before/after;
- minimum notice;
- maximum advance;
- date exceptions;
- blocked periods;
- existing active bookings.

The backend revalidates the selected interval at booking creation and PostgreSQL prevents active overlapping bookings for the same bookable resource.

Future staff/provider-specific calendars are a separate capability and must only be introduced if Castro’s business operations require multiple simultaneous providers for the same service.

## 6. Implementation sequence

### Block A — Architecture lock
- Canonical persona document (this file).
- Screen × Permission matrix.
- Update implementation checklist to reflect four experiences.

### Block B — Secretary experience
- Replace generic dashboard with a dedicated operational dashboard.
- Secretary-first navigation hierarchy.
- Preserve existing Operations functionality and permission enforcement.

### Block C — CEO / Owner experience
- Dedicated `/owner` layout/navigation.
- Executive dashboard based only on real operational/report data.
- Executive overview screens/read-oriented drill-down.
- Optional advanced-administration entry point.

### Block D — RIGHTWARE Super Admin foundation
- Separate platform authority model.
- Separate `/platform` security boundary and layout.
- Platform dashboard and organization inventory foundation.
- No tenant impersonation or silent cross-tenant access.

### Block E — Persona regression gates
- Route/access tests for all four experiences.
- Navigation visibility tests.
- Permission/action tests.
- Cross-organization/platform isolation tests.

### Block F — Visual/responsive/accessibility QA
Only after Blocks A–E are stable should the final P5 polish be considered authoritative.
